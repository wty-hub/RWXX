# Windows 快速拖图优化实现记录

更新日期：2026 年 10 月 4 日。

本文记录本轮已经保留的地图显示、内存复用、输入和帧节奏改动，重点是正常游戏与动态拖图时的短停顿。当前已保留直接绘制地图格、像素及上传缓冲池、不可变像素共享、光栅快路径和文字网格复用。更激进的等待策略及原生 BGRA 上传保留为实验开关，默认关闭。

这些改动降低了多条路径的重复工作，但没有证明所有短停顿已经消失。正常游戏、回放中的同步重载、GPU 原生调用和系统调度必须分别分析。较早的 Linux、macOS 和 Windows 结果见 [桌面端卡顿优化说明](desktop-performance.md)；当前线程与资源模型见 [原版引擎与 Vulkan 渲染分离](vulkan-engine-separation.md)。

用户最新反馈仍是指定欧洲地图正常联机对局中手动拖动时 `new` 暴降，连续放缩时更明显；开启迷雾和死亡后迷雾消失时均有卡顿。该问题继续排查；下文的有限自动测试结果不能覆盖这次实际交互，也不能将迷雾视为唯一原因。

## 指标与验证范围

`render` 是后端接受呈现的频率，重复显示同一个引擎画面也会计数。`new` 是呈现时采用新画面的频率；`engine` 是完成 CPU 画面的频率；模拟 tick 推进率另行记录。因此，较高的 `render` 不能证明地图拖动流畅，也不代表显示器的物理扫描帧率。

本轮主要检查新画面间隔的 P95、P99、超过 16.667／33.333／50／100 毫秒的次数，并结合重复比例、CPU 和资源计数判断效果。平均帧率改善与罕见长帧改善分别报告。

动态对照实际运行 Vulkan 游戏，使用内置 Interlocked Large 地图、500 个正常构造的移动单位、15 个队伍和六种陆空单位。相机每秒往返一次，覆盖约 1600 世界单位的横向及纵向范围。单位接收正常移动命令；交战模式遵守正常伤害与战损规则，没有无敌或自动补员。

正式对照采用 A B B A 四次独立启动，每进程预热 20 秒、随后采样两个 20 秒窗口。每侧约 80 秒的窗口并集用于长帧计数。正式性能对照关闭 JFR 和逐阶段 Vulkan 诊断；这些诊断单独用于归因。自动相机运动验证快速视口移动，不等于物理鼠标或屏幕扫描输出验收。

## 地图显示与光栅化

### 地图格直接绘制与滚动缓存

Kool 将地图内容直接绘制到对应 cell，省去共享 scratch 到目标格的整格复制。每次重绘先清理完整目标，再绘制地形、细节、焦痕及需要显示的迷雾；其他后端保留原有复制路径。实现位于 `LayerBufferManager.java` 和 `KoolGraphicsEngine.kt`，回归测试覆盖透明边界、迷雾、焦痕、缩放及旧格清理。

地图格默认仍为 512×512 像素，增加一层外围格子。提前滚动请求边距为 256 世界单位，并根据实际剩余覆盖空间夹紧；滚动阈值、格子重叠和多格平移保持一致，避免视口边缘反复来回滚动。多格平移保留重叠格子的世界坐标，超出缓存覆盖范围才全部重建。调整视口或缓存尺寸后重置相机采样。

可见的 dirty 格子在画面发布前全部完成。画面发布后，按相机运动方向、预计进入时间和视口距离预热屏外地形，预算为 2 毫秒，但至少允许完成一格。单格重绘不能中途打断，因此这不是每帧严格不超过 2 毫秒的保证，也不能保证任意速度拖动都不会触发可见格重绘。

对应文件：`core/src/main/java/com/corrodinggames/rts/game/map/LayerBufferManager.java`、`MapLayer.java`，以及 `core/src/main/kotlin/io/github/rwx/render/canvas/KoolLayerBufferSizing.kt`、`KoolGraphicsEngine.kt`。

### 迷雾显示的条件跳过

关闭迷雾显示时，地图格跳过独立 fog pass 与逐格迷雾数据读取。Kool 不使用旧的双缓冲平滑淡出路径。回放视野关闭或没有新的模拟 tick 时，独立的回放视野维护也会提前返回。

这不等于删除全部迷雾逻辑：`MapLayer` 仍调用 `ensureFogCacheAllocated()`，真实队伍视野及其同步数据继续维护。正常迷雾周期的最终像素差分候选已撤回，没有作为当前优化启用。

### CPU 像素快路径

标量坐标映射直接计算逆变换后的采样坐标，避免逐像素创建坐标对象。原有算术顺序、舍入及失败行为通过矩阵与像素对照保留。

当目标像素不透明时，SourceOver 使用专用路径，省去通用透明目标的处理。它保留逐通道取整和预乘颜色饱和规则；不满足条件的像素仍走通用路径。`KoolRasterScalarMappingTest` 和 `KoolOpaqueSourceOverTest` 验证输出，而不是仅验证实现分支被调用。

并行光栅默认使用 CPU 数量减一，并夹至 1–4 个 worker。只有处理像素至少 65536 且行数至少为 worker 数的 16 倍时才并行；小图块通常串行。`rwx.koolRasterThreads` 可显式设为 1–8。

## 像素共享与有界内存池

光栅结果以独占像素 owner 注册；完成的帧共享其只读版本，避免每帧重新复制同一份大数组。legacy `Texture` 要写入仍被旧帧持有的数组时使用 copy on write，保护旧画面。完整清理并替换目标时跳过旧像素解析和复制；增量更新仍复制需要保留的内容。

像素、帧资源和上传缓冲各有独立的租约。替换待显示画面并不意味着它引用的全部内存已经可复用：当前显示画面、嵌套帧和 GPU 在途资源可能仍持有租约。只有相应使用者全部退出，才归还存储。失败路径、worker 退出握手、重复关闭和世代检查防止提前回池或把旧 context 的存储放进新池。

| 存储 | 当前闲置保留上限 | 预分配与回收规则 |
|---|---:|---|
| CPU `IntArray` 像素池 | 64 MiB，每个精确尺寸最多 64 个数组 | 地图常用目标尺寸首次建立时最多预分配 48 个；512² 对应 48 MiB，仍受总容量约束。最后一个像素 owner 释放后回池 |
| ARGB host 上传缓冲池 | 64 MiB，每个精确尺寸最多 64 块 | 复用纹理上传 owner；实际 GPU 退役后回池。已有预分配 API，当前生产路径没有调用 |
| 静态精灵图集上传缓冲 | 最多两块默认大小缓冲，共 32 MiB | 图集页为 2048×2048，最多四页；上传使用独立缓冲，旧版本实际退役后才能复用 |

上述容量限制的是各池的闲置存储，不是活动租约、GPU staging 或进程总内存。预分配将常用尺寸的首次分配提前，但仍可能因新尺寸、池未命中或同时活动资源增多而分配。对象、命令列表和几何增长也仍会分配，因此不能写成消除了 GC。

对应实现：`KoolCanvasPixelPool.kt`、`KoolCanvasUploadBufferPool.kt`、`KoolCanvasResources.kt`、`KoolCanvasFrameEnvelope.kt`、`KoolCanvasSpriteAtlas.kt`、`KoolGraphicsEngine.kt`，以及 `core/src/main/kotlin/com/corrodinggames/rts/gameFramework/graphics/Texture.kt`。

### 纹理命中路径的小对象复用

正常游戏 JFR 指出了纹理注册元数据的分配热点。当前命中路径直接比较已有记录与纹理的尺寸、真实像素修订号及预乘标记，避免为比较创建新的 `TexturePixelRegistration`。IMMEDIATE 纹理继续核对当前 image／frame 的身份和 alpha bleed 标记；屏外像素快照仍核对 source image，保护旧帧。

root 与屏外绘制共享弱键元数据缓存，复用纹理 ID 字符串和字段完全相同的不可变 `TextureRef`。缓存值不持有纹理的强引用；legacy ID、尺寸及 alpha 等字段改变时发布新引用，纹理释放时删除记录。默认启用，`RWX_DISABLE_TEXTURE_METADATA_REUSE=1` 可回退。四项新增测试覆盖字段失效、旧像素租约隔离和释放清理；这项改动的性能收益仍须在连续缩放与正常联机中复测。

## Vulkan 上传与网格复用

现有 Vulkan 路径复用常驻映射 staging，按实际 fence 管理在途资源；贴图上传并入主帧命令流，不为每张动态贴图单独等待整队列。本轮保留该模型及完整同步屏障，没有投用缩窄屏障的候选。

静态精灵图集将逐字节拷贝改为整页批量写入独立 host 缓冲。图集增长不会修改旧 `ImageData` 所引用的内存，缓冲仅在实际退役后进入图集池。

冻结像素网格按 CPU store owner 和逻辑像素身份复用，纹理版本更新时重新绑定实际 GPU 纹理。同帧多个历史版本使用独立 slot；过滤、混合和排序约束继续参与缓存键。相关测试验证旧版本和 owner 隔离。

文字网格复用解决了另一种缓存抖动：相机移动会改变前面的绘制批次数，相同文字原先会因为批次序号变化而重新创建网格、着色器和直接缓冲。现在先查原有完整缓存键，未命中时可取本帧尚未使用的顶层有序文字网格，要求真实 `fontData` 为同一引用，并匹配混合模式、typeface 和性能 HUD 类别。

复用后仍重写文字内容、裁剪和变换，重新指定绘制顺序；同帧同时出现的文字批次不会共享同一个 owner。投影展开中的文字不进入这条复用分支。场景切换不借用旧场景网格，闲置网格仍走 fence 退役。七项新增测试覆盖网格、着色器和缓冲身份，几何逐位比较，字体 atlas 替换，HUD 隔离及延迟回收。

文字计数记录累计创建、精确命中、复用、回收、扫描候选数以及当前数量和历史峰值。它们随已有的五秒诊断样本输出，没有逐次网格事件 I/O；计数不是直接测得的分配字节量或 GC 节省量。

对应实现：`core/src/main/kotlin/io/github/rwx/render/canvas/KoolCanvasFrameRenderer.kt`、`CanvasFrameMetrics.kt`、`KoolCanvasSpriteAtlas.kt`，以及 `desktop/src/main/kotlin/io/github/rwx/kool/vulkan/VulkanUploads.kt`、`VulkanFrameLifecycle.kt`。

## 输入窗口与帧节奏

### 指针转发与窗口布局

正常指针路径只在 render frame 完成 poll 后转发一次新样本，去掉旧 listener 和非 render drive 的重复转发。按下、抬起、滚轮、失焦释放、模态窗口阻挡及所见相机捕获仍保留。所有者队列继续按 FIFO 执行，快速按下与释放分别经过完整引擎循环。五项指针测试验证实际 sink 接收的事件。

Swing 首次布局完成后，使用当前屏幕的 AWT 逻辑坐标，将初始窗口尺寸夹至可用工作区，并计入任务栏及窗口装饰；之后保留用户手动缩放。该修复针对初始窗口在高 DPI 或较小笔记本屏幕上的超出工作区问题，不能替代全部多屏 DPI 切换场景验收。重复设置相同鼠标光标时也跳过 Swing 更新。

尚未首次提交的 generated target 注册有效的空画面，降低正常加载期间出现品红方块的机会。真正缺失或解码失败的资源仍保留品红棋盘提示。

对应实现：`core/src/main/kotlin/io/github/rwx/app/InputController.kt`、`FrameDriver.kt`，以及 `desktop/src/main/kotlin/io/github/rwx/SwingKoolHost.kt`、`SwingWindowSizing.kt`。

### 引擎与呈现等待

当前游戏循环由独立 `EngineOwnerLoop` 运行，呈现线程消费完成的 CPU 画面；该基础模型已在渲染分离文档中说明。旧文档关于游戏循环内联于 Kool 回调的段落属于历史记录。

本轮默认保留高刷新模式的混合等待：当外层周期不超过 3.333333 毫秒时，较粗的剩余时间使用 park，最后 1.5 毫秒使用 `Thread.onSpinWait()`。每次等待都返回外层循环，继续检查输入、重置和关闭。设置回调每个 tick 完成后读取一次。低刷新和节电模式保持原节流方式，没有改变原版模拟累积器。

Kool 呈现等待的粗阶段每次最多 park 2 毫秒并轮询窗口事件，最后 0.1 毫秒自旋。两处等待策略用途不同，不应合并计算自旋预算。

更严格的 owner 粗等待保护仅在 `RWX_GUARD_SHORT_OWNER_PARK=1` 时启用：减去 1.5 毫秒后，请求不足 1.5 毫秒就改为自旋。这使最终自旋可能延长到约 3 毫秒。实测额外 CPU 代价明显，当前默认关闭。等待策略无法保证操作系统不抢占线程，也不能消除 GC 或原生 GPU 调用的等待。

对应实现：`desktop/src/main/kotlin/io/github/rwx/kool/EngineOwnerLoop.kt`、`KoolDesktopGameSession.kt`、`desktop/src/main/kotlin/io/github/rwx/KoolFramePacer.kt`。

## 回放视野及重载相关改动

回放增加本地视野菜单，可切换迷雾显示和玩家视野。独立的回放视野状态按模拟 tick 更新，合并相同圆形视野及同盟接收者；关闭时跳过这项显示维护。视野快照与回放 seek checkpoint 配合恢复，不写入原版回放或网络数据。单位可见性和小地图显示入口识别回放的观察者状态；正常对局仍使用原有队伍视野。

实现涉及 `ReplayEngine.java`、`ReplayFogState.java`、`ReplayVisionControls.java`、`GameInterfaceRenderer.java`、`Minimap.java`、`BaseUnit.java` 及中英文翻译。该功能与迷雾性能候选不同；当前保留回放视野功能，已撤回正常迷雾周期的最终差分候选。

此前也已落实三项重载优化，继续保留，但它们不计入正常游戏短停顿的收益：

1. Kool 保存或网络恢复式载图跳过一处及末尾五处主动 `System.gc()`。初次载图与要求原策略的后端仍使用旧行为；`RWX_FORCE_LEGACY_RELOAD_GC=1` 可恢复旧策略。
2. 队伍迷雾数据按原有列序使用 raw byte slice 读写，维持相同序列化字节。畸形维度和数组分支回退，保留原有异常及流消费顺序。
3. 恢复脚本触发器时构建仅用于本次恢复的大小写无关索引，重复 ID 保留首个匹配，缺失和畸形情况保留原查找规则。

实现位于 `GameLogic.java`、`PlayerTeam.java`、`GameInputStream.java`、`GameOutputStream.java`、`DebugOutputStream.java` 和 `MissionEngine.java`。地图及脚本仍会按原流程重建。本轮后续排查按要求暂不优化同步重载停顿。

## 已验证的性能效果

下表中的各行来自不同阶段和尺寸的独立对照，不能相乘、相加，或将某一行解释为当前版本相对所有旧版本的总收益。分位数是各采样窗口指标的中位数；合并样本分位数另保存在验证数据中。

| 改动与场景 | 新画面频率 | 新画面间隔 P95 | 新画面间隔 P99 | 限制 |
|---|---:|---:|---:|---|
| 不透明目标 SourceOver，1920×1080，动态 500 单位，开迷雾 | 108.15→170.74 次每秒 | 25.37→12.66 ms | 48.71→21.17 ms | 对应该阶段的受控对照，不能作为其他尺寸结果 |
| 默认 owner 混合等待，1600×900，动态 500 单位，关闭迷雾 | 222.22→234.08 次每秒 | 7.81→6.82 ms | 9.27→8.73 ms | Java CPU 中位数增加约 3.38 个百分点，罕见长帧未消失 |
| 文字网格复用，1280×720，动态 500 单位，关闭迷雾 | 234.12→236.81 次每秒 | 6.33→5.87 ms | 8.67→8.43 ms | Java CPU 中位数 15.945%→16.285%，部分窗口仍重叠 |

文字计数使用两端点都位于同一测量窗口内的五秒计数区间，每侧有效覆盖约 70.03 秒，占约 80 秒测量窗口的 87.53%。这部分区间内，创建 **867→0**，回收 **876→0**，新策略完成 **9686** 次复用；新策略每进程记录到的缓存数量和峰值均为 9。启动期累计创建 9 个与测量期新增 0 个是不同指标。

该文字对照中，双方均没有超过 33.333 毫秒的间隔，超过 16.667 毫秒的次数为 2→0。这段有限采样不能证明罕见顿挫消失。后续粗等待保护复测双方仍各出现一次超过 50 毫秒的间隔。

指定欧洲回放完成真实 Vulkan 验证，实际窗口 1280×720，包含约 500 个单位、移动及交战。排除同步重载本体后采样 39.50 秒，P99 为 8.32 毫秒，没有超过 33.333／50／100 毫秒的间隔；最大 26.70 毫秒属于重载后的地图缓存预热尾段。另一个正常 21.25 毫秒间隔与 5.21 毫秒 GC 暂停及图集上传重叠，18.91 毫秒间隔中 owner 快照阶段耗时 8.24 毫秒。重叠和采样栈不证明整段连续 CPU 时间，也不证明某一次上传分配触发了 GC。

这组欧洲回放固定 `zoom=1`、关闭迷雾显示、绕地图中心平移。代码审计发现，缩放跨过缓存比例阈值会将整个地图格网标为 dirty；可见格在 owner 发布画面前同步完成重绘。缩小时单格覆盖的世界面积增大，逐瓦片工作和可见单位也可能增加。原来的稳定门槛按帧计数，高刷新时更快达到门槛；这些是连续放缩测试的候选原因，尚未证明是用户顿挫的唯一原因。

用户反馈后，直接对正在运行的正常游戏实例附加 70 秒 JFR。owner 的 5830 个 CPU／原生采样中，2011 个包含地图格重绘；107 个 GC 暂停事件累计约 826 毫秒，最长约 22.15 毫秒。分配采样的主要热点是 `TexturePixelRegistration` 和非 ASCII `Character`，另有绘制命令、矩形、paint 及纹理 ID 字符串。采样权重是估计，不能作为精确分配字节；这组记录缺少同步的新画面提交时间，不能逐次对齐用户看到的顿挫。它支持继续减少命中路径的小对象，而不只处理大数组。

回放文字缓存稳定为 14 个条目，窗口内计数区间创建、回收均为 0。JFR 与单调时钟使用 88 个有效 marker 对齐，最大校准残差约 3.85 微秒。较早回放测试实际为 1600×900，因此不能用本轮数值与其直接相减宣称因果改善。

持久化的指标、包和回放 SHA256、测试范围及实验结论见 [Windows 拖图验证数据](verification/windows-map-pan-optimization-2026-10-04.json)。原始帧、JFR、日志和运行包保留在本机 `build/map-pan-*`，不随源码提交；回放原文件没有修改。

补充运行包 `europe-zoom-metadata-controlled-16.jar` 构建成功，190 项受影响 core 测试、108 项 desktop 测试通过，包含四项元数据、五项缩放节拍和四项连续缩放诊断测试。35 项 Python 工具测试通过。上述通过结果验证功能与资源规则，不代表新的性能对照已经通过。

本轮没有宣称全核心测试、全部存档恢复、全部网络互通或全部 GPU 图像等价验收通过。此前缺少完整回放样本的 `ReplayTimelineIndexTest` 及旧文档中的其他夹具限制，不能被这些受影响模块的通过结果覆盖。较早的原版引擎类字节一致证明属于较早运行包，当前有地图、回放视野及恢复代码变更，不能沿用该证明。

正常游戏仍有 GC、快照处理、首次资源准备、原生提交及系统调度造成短停顿的可能。后续优化应继续用同一时钟的区间和实际分配证据确定对象及生命周期；已有池不能被视为整个渲染路径零分配，也不能承诺任意快速拖图都没有顿挫。
